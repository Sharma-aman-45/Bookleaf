# BookLeaf Author Support & Communication Portal

A web app for BookLeaf Publishing with two sides:

- **Author portal**: authors sign in, see their books and royalties, raise support tickets and follow replies live.
- **Admin portal**: the operations team works a prioritised ticket queue. AI classifies each ticket and drafts replies grounded in the BookLeaf knowledge base. The admin edits the draft and sends it.

## Architecture decisions

**Layering.** Route handlers stay thin: parse and validate input, call a service, return the result. Services hold the business rules (who can see what, status transitions, assignment, audit events). The AI layer is isolated in `lib/ai` and never touches HTTP or the UI. This keeps each piece small and testable, and lets the AI provider be swapped without touching tickets.

**One route wrapper for every endpoint.** `route()` in `lib/api/handler.ts` authenticates the request (cookie session or `Bearer` token), loads the profile and role, enforces the allowed roles, awaits the params, and converts any thrown error into the standard error shape. No endpoint can forget authentication.

**Access control in two places.**
1. The API checks ownership in the service layer. An author asking for another author's ticket gets a 404, so ticket IDs are not confirmed to exist.
2. Postgres row-level security enforces the same rules for the browser's Realtime connection, which uses the public anon key. Authors only receive change events for their own tickets. Internal notes, AI drafts and usage logs are admin-only at the database level.

All writes go through the API using the service-role key, which exists only on the server (`import "server-only"` makes the build fail if it is ever imported into client code).

**Schema.** Status, priority and category are Postgres enums. The priority enum is declared in order `critical, high, medium, low`, so sorting by priority puts the most urgent first with no extra code. Tickets record where their category and priority came from (`ai`, `fallback` rules, or `admin`), which drives the UI chips, protects admin overrides from being replaced by reclassification, and powers the accuracy metric. `ticket_events` is an audit log of every status change, override, assignment and reply. Books keep the original dataset record in a `metadata` JSON column so nothing from the source data is lost.

**Real time.** Pages subscribe to Postgres changes for exactly the rows they show (one ticket, or one author's tickets) and refetch through the API on change. Refetching keeps the API as the single source of truth and avoids leaking fields through the socket. If the subscription is not connected, the hook polls every 15–20 seconds while the tab is visible.

**Ticket creation never waits on AI.** The ticket is saved and returned immediately. Classification runs after the response using Next.js `after()`, then updates the row, and Realtime pushes the update to the admin queue.

## How the AI integration works

### 1. Classification (category and priority)

- **Model:** small and fast (`llama-3.1-8b-instant`), temperature 0, JSON output mode, 120 max output tokens.
- **Input:** subject, the first 1,500 characters of the description, and the book's production status. The knowledge base is not sent: classification needs category definitions and a priority rubric, not policy text.
- **Prompt:** defines the six categories with hints for borderline cases, and a priority rubric derived from the brief (for example, months of missing royalties is critical, a bio update is low).
- **Output check:** the JSON is validated with Zod. Anything malformed falls back to rules.
- **Policy guardrails:** after the model answers, deterministic rules enforce BookLeaf policy. An ISBN mismatch is always at least High (the knowledge base says ISBN errors are high priority). Long-unpaid royalties, legal threats and piracy are raised to Critical. The model cannot under-prioritise these.
- **Overrides:** admins can change category or priority at any time. Overrides are marked `admin` and are never replaced by a later reclassification.

### 2. Drafted replies

- **Model:** a stronger model (`llama-3.3-70b-versatile`) because tone and accuracy matter here.
- **Prompt structure:**
  - *System:* the agent's real name, BookLeaf tone guidelines, only the knowledge-base sections for this ticket's category, the brief's sample queries for that category with how to respond, and strict rules (use only provided facts, never invent numbers, 90–180 words, sign off as the agent).
  - *User:* today's date, the author's name, the book record, the ticket, and the conversation so far.
- **Grounded numbers:** the server computes facts the model should not guess. For royalty tickets it adds earned, paid and pending amounts, the current quarter end and the payout-by date (quarter end + 45 days), and whether the pending amount is below the ₹1,000 threshold. This is how drafts can say "your next payout is due by 14 November" accurately.
- **Reviewer instructions:** the admin can type a short instruction ("shorter", "ask for bank details") and regenerate.
- **The admin always reviews.** Drafts are never sent automatically. Replies sent from an AI draft are flagged `ai_assisted` for reporting.

### 3. Cost management

| Technique | Effect |
| --- | --- |
| Category-scoped knowledge base | Each draft gets one or two policy sections, not the whole knowledge base |
| Category-scoped book facts | Royalty figures are only included for royalty and general tickets |
| Thread window | Only the last 4 messages, each capped at 600 characters, with a count of omitted messages |
| Input truncation | Description capped at 1,500 characters, subject at 200 |
| Two model sizes | The cheap model handles every ticket; the larger model only runs when an admin opens a ticket |
| Draft cache | Drafts are cached by a hash of category, last message and instruction; reopening a ticket costs nothing |
| Output caps | 120 tokens for classification, 450 for drafts |
| Usage logging | Every call logs model, tokens, latency and errors to `ai_usage`, shown on the Insights page with an estimated cost |

A typical royalty draft prompt is about 700–800 input tokens.

### 4. Graceful degradation

| Failure | What happens |
| --- | --- |
| No API key configured | Tickets are classified by keyword rules; drafts load a policy template; the UI says so |
| Rate limited (429) | One retry if the wait is 3 seconds or less, otherwise a cooldown that skips AI calls until it expires, so a busy queue does not hammer the provider |
| Timeout or 5xx | One retry for server errors, then fallback |
| Malformed model output | Zod rejects it and keyword rules classify the ticket |
| Any AI failure | The ticket is still created, the admin can still write and send a reply, and the failure is logged and visible on the Insights page |

Every fallback is labelled in the UI ("Rules" chip on the category, "Policy template" chip on the draft) so admins know when to double-check.

### 5. Model choice

I used **Groq** with Meta's **Llama 3.1 8B** for classification and **Llama 3.3 70B** for drafts.

- It has a free tier, which the brief allowed ("use your own API key").
- Groq is very fast, so drafts appear in a second or two when an admin opens a ticket.
- It exposes an OpenAI-compatible API. The client only depends on `AI_BASE_URL`, `AI_API_KEY` and the model names, so switching to OpenAI `gpt-4o-mini`, Claude Haiku via a compatible gateway, or xAI is a configuration change, not a code change.
- Splitting by task keeps cost low: classification runs on every ticket and needs a cheap, deterministic model; drafting runs less often and benefits from a stronger one.

## API overview

All endpoints are under `/api/v1`. Full request and response schemas are in `/docs`. The `openapi.yaml` file can also be imported into Postman.

| Method | Path | Role | Purpose |
| --- | --- | --- | --- |
| POST | `/auth/login` | public | Sign in; returns profile and access token, sets cookie |
| POST | `/auth/logout` | any | Sign out |
| GET | `/me` | any | Current profile |
| GET | `/books` | any | Books with royalty summary (authors: own only) |
| GET | `/books/{id}` | any | One book (authors: own only) |
| GET | `/tickets` | any | List with filters: status, category, priority, assigned, from, to, q, sort |
| POST | `/tickets` | author | Raise a ticket |
| GET | `/tickets/{id}` | any | Ticket, messages; admins also get notes, activity, AI reasoning |
| PATCH | `/tickets/{id}` | admin | Status, category or priority override, assignment |
| GET, POST | `/tickets/{id}/messages` | any | Read or send replies |
| GET, POST | `/tickets/{id}/notes` | admin | Internal notes |
| POST, DELETE | `/tickets/{id}/assign` | admin | Assign to self, or unassign |
| GET, POST | `/tickets/{id}/draft` | admin | Get cached draft, or regenerate with an instruction |
| POST | `/tickets/{id}/classify` | admin | Re-run classification |
| POST | `/uploads` | author | Upload an attachment (PNG, JPG, WEBP, PDF, max 5 MB) |
| GET | `/admin/stats` | admin | Queue counters |
| GET | `/admin/ai-insights` | admin | AI usage, cost and override metrics |
| GET | `/admin/users` | admin | Admins, for assignment |

Error format, used for every failure:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Some fields are missing or invalid.",
    "details": [{ "field": "subject", "message": "Subject must be at least 5 characters." }]
  }
}
```

Status codes used: 400 bad JSON, 401 not signed in, 403 wrong role, 404 missing or not yours, 409 invalid state (replying on a closed ticket), 413 file too large, 415 file type not allowed, 422 validation, 500 unexpected.

Example with curl:

```bash
TOKEN=$(curl -s -X POST http://localhost:3000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@bookleaf.in","password":"Admin@123"}' | jq -r .data.access_token)

curl -H "Authorization: Bearer $TOKEN" "http://localhost:3000/api/v1/tickets?status=open&sort=urgency"
```

## Product decisions

- **Urgency-first queue.** Default view is active tickets sorted by priority, then age. Each row has a coloured priority spine, and rows past their first-response target (Critical 4h, High 24h, Medium 48h, Low 72h) are marked late.
- **Counters that act as shortcuts.** "Unassigned" and "Assigned to me" filter the queue in one click.
- **Context next to the reply.** The admin sees the book's status, ISBN and full royalty figures beside the draft, so they can check the AI's numbers at a glance.
- **Stale draft warning.** If the author replies after a draft was generated, the admin is prompted to update it.
- **Edge cases on My Books.** Books in production explain that royalties start after going live; zero-sales books explain listing timelines; small pending balances explain the ₹1,000 rollover.
- **Helpful ticket form.** Typing about print quality suggests attaching photos; royalty questions prompt for the quarter and bank status. This reduces back-and-forth.
- **Ticket lifecycle.** An admin's first reply moves the ticket to In Progress and assigns it to them. An author replying on a resolved ticket reopens it. Closed tickets point the author to raise a new one.

## Known limitations and what I'd do next

- **Classification runs once.** If an author's follow-up changes the topic, the admin must reclassify manually. Next: reclassify on author replies when the confidence was low.
- **Keyword fallback is basic.** It handles all seven sample queries correctly but would miss unusual phrasing.
- **No vector retrieval.** The knowledge base is small enough to select by category. For a large help centre, I'd embed articles and retrieve the top few per ticket.
- **No email notifications.** Authors only see replies in the portal. Next: send an email on admin reply, using the same draft content.
- **Rate-limit cooldown is per server instance.** On serverless it resets between cold starts. A shared store (Redis or a database row) would make it global.
- **No automated tests yet.** The AI pipeline was tested against a mock provider (including a 429 retry), and the fallback classifier against the brief's sample queries. Next: unit tests for services and the royalty schedule, and contract tests for the API.
- **Draft quality evaluation.** Next: an offline set of labelled tickets to measure classification accuracy and check drafts for invented numbers before changing prompts or models.
